## Medium

### M1. Monthly reminder drift for day-of-month 29/30/31
- **Location:** `addon/app/reminders.py:27-43` (`_add_period`, `monthly` branch).
- **Problem:** `_add_period` clamps the target day to the destination month's
  length using the *current* dt's day, not the original scheduled day. Once a
  monthly reminder on day 31 passes February and is stored as Feb 28, every
  subsequent `_add_period(dt, "monthly")` starts from `dt.day == 28` and never
  restores to 31. The reminder permanently drifts to the 28th.
- **Evidence:** `day = min(dt.day, calendar.monthrange(year, month)[1])` — `dt`
  is the *last-fired* datetime, so after one Feb clamp the anchor is lost.
- **Suggested fix:** Store the original `day_of_month` alongside the reminder
  (or re-derive it from `send_at`'s creation month) and clamp against that
  every time, not the running datetime.
- **Impact:** monthly reminders scheduled for the 29th/30th/31st drift down
  after the first short month and never come back up. Pre-existing bug, not
  introduced by the refactor, but the review should flag it before deploy.

### M2. `_EXPENSE_SUMMARY` broadcasts a read-only query to the household
- **Location:** `addon/app/claude_agent.py:135-138` (`BROADCAST_TOOLS`) +
  `addon/app/agent_loop.py:222` (`tools_used & BROADCAST_TOOLS`).
- **Problem:** `_LIST_RECENT_EXPENSES` is *not* in `BROADCAST_TOOLS`, but
  `_EXPENSE_SUMMARY` is. Both are pure reads. Asking "how much did we spend
  this month?" today pushes the summary to the spouse's WhatsApp as an
  unsolicited message.
- **Suggested fix:** either remove `_EXPENSE_SUMMARY` from `BROADCAST_TOOLS`
  (aligning it with `_LIST_RECENT_EXPENSES`), or promote both. Reads probably
  shouldn't broadcast — only mutations should.
- **Impact:** noise for the other spouse; not a data leak (they're already in
  the household), but at odds with CLAUDE.md's "everything else is private."

### M3. Auto-turn-off is in-memory only; lost on restart
- **Location:** `addon/app/handlers/scheduled_actions.py:27-34`
  (`_auto_turn_off_later`); scheduled from `addon/app/loops.py:110-112` and
  from the immediate device turn-on path.
- **Problem:** the follow-up "turn off after N minutes" is an unrecorded
  `asyncio.create_task` sleep. If the add-on restarts, upgrades, or crashes
  during that sleep, the device stays on and the user gets no message.
- **Suggested fix:** persist auto-off as a scheduled_action row (turn_off at
  now + N min) so it survives restarts via `_scheduled_action_loop`.
- **Impact:** a scheduled AC/light left "auto-off in 2h" during a redeploy
  window silently keeps running. Realistic scenario given end-of-phase
  deploys.

## Low

### L1. Fragile ✅-string check gates the auto-off follow-up
- **Location:** `addon/app/loops.py:109`
  (`if a.duration_minutes and a.service == "turn_on" and "✅" in reply:`).
- **Problem:** the loop uses the reply string as a success signal. If
  `_execute_control_action` ever changes its success format (or a description
  ever contains ✅), the branch silently misbehaves.
- **Suggested fix:** have `_execute_control_action` return `(ok, reply)` and
  branch on `ok`. Same pattern as `ha_client.call_service`.

### L2. `pop_if_confirmed` only checks the first action's expiry
- **Location:** `addon/app/confirmation.py:32`
  (`if time.time() > actions[0].expires_at`).
- **Problem:** if a list of pending actions ever mixes different TTLs, only
  index 0 is checked. Today all actions share a TTL (they're queued together
  in one turn), so this is latent, not live.
- **Suggested fix:** check `min(a.expires_at for a in actions)`.

### L3. `store_pending` overwrites any prior pending set silently
- **Location:** `addon/app/confirmation.py:22-23`, called from
  `agent_loop._handle_message` after each turn's `pending_actions`, and from
  the scheduled-action loop when a risky action falls due.
- **Problem:** if a risky scheduled action fires while the user has an
  unrelated pending confirmation, the earlier pending is silently dropped and
  a subsequent "yes" confirms only the newer one. User expected to confirm
  the earlier action.
- **Suggested fix:** append instead of overwrite, or reject-and-warn if
  pending already exists.

## Nit / Rough edges

### N1. Compat aliases `_from_dict = _store._from_dict` in 12+ store modules
- **Location:** every store module listed by
  `grep -n "_from_dict = _store._from_dict" addon/app/*.py`.
- **Note:** exists so `tests/test_regressions.py` can reach in via the
  module-level name after Item 05. Preserves unknown-key defense; the tests
  parametrise over each of these aliases and assert the filter. Correct but
  ugly; safe to keep until tests are rewritten to use `_store._from_dict`
  directly.

### N2. `main.py` "canary comment" for the regression scanner
- **Location:** `addon/app/main.py:139-142`.
- **Note:** a comment kept only so `tests/test_regressions.py`'s text scan
  still finds the `inp.get("source") or "manual"` string after Item 06 moved
  the real code to `handlers/expenses.py`. Works, but the test would be more
  honest scanning `handlers/expenses.py` directly.

### N3. Unused / redundant re-exports in `main.py`
- **Location:** `addon/app/main.py:22-136` — ~100 lines of `# noqa: F401`
  re-exports. Necessary today because tests reach in via `app.main.X`; every
  new symbol added to main's surface is now a public commitment. Consider a
  test-side migration to importing from the split modules directly in a
  future cleanup item.

### N4. Meta-window loop cannot self-trigger
- **Location:** `addon/app/loops.py:168-200` (`_meta_window_loop`) +
  `agent_loop._process_message` calling `inbound_tracker.record_inbound`.
- **Note:** verified the outbound 23h warning does NOT reset
  `entry.last_inbound_at`. `record_inbound` is only called from
  `_process_message` on real inbound. Warning is idempotent per cycle via
  `warned_23h`. Safe.

### N5. `_require_lan` is not X-Forwarded-For spoofable
- **Location:** `addon/app/status.py:123-128`.
- **Note:** uses `request.client.host` (TCP peer), not headers. Correct.
  Docstring already warns not to point a public reverse proxy at this route;
  if a proxy is added later, host will be the proxy's IP and the current LAN
  check still applies to whichever process the proxy runs on.

## Store atomic-write audit

Spot-checked every writer in `addon/app/*.py` against `Store.save_list` /
`Store.save_dict`. All persistent writes flow through `Store`, which does
`tmp.write_text(...) + os.replace(tmp, p)`. `os.replace` is atomic on Windows
and POSIX (the deployed platform is Linux via HA add-on; dev is Windows). No
codepath writes the target file directly.
